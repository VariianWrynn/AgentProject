基线为 main 的 `f0d9c635a264074e3a7b1d0ffc778ae0759392c9`，已包含 PR #27 的 SQL 修复与首批清理。目标是面向简历展示的 Linux 单机站点，4 vCPU、8GB 内存、无 GPU，模型和搜索使用外部 API。为避免 GB/GiB 混淆，本轮保守采用全机不超过 **8,000,000,000 字节** 的验收边界。实际限额必须记录，不能把 8GB 分别分配给每个服务，也不能将 8GiB 测试结果标为这个更严格边界的通过结果。

## 轻量向量模型的边界

首个候选为 `BAAI/bge-small-zh-v1.5`，面向中文。官方配置的 hidden_size 为 **512**，最大位置长度为 512，不是英文 small 模型的 384 维。来源为 [官方配置](https://huggingface.co/BAAI/bge-small-zh-v1.5/blob/main/config.json)。最终模型 revision 在实现时固定。

不能把旧集合的 1024 改为 512 后继续使用原向量。先建立独立的新集合，从原始文本重新编码，校验文档/分块数量和来源映射，再切换配置。旧集合保留作回退，本轮不删除数据。即使两个模型维度相同，也不能混用不同 embedding 空间。

同时调整 tokenizer 分块窗口、查询指令与检索过滤。当前 `backend/agents/deep_scout.py:77` 的 RAG score>=0.3 是旧模型门槛，不能凭经验原封不动视作新模型质量保证。用固定中文事实问答、数字/专名及必要英文资料比较可支持答案的召回，不要求 E 编号或排序完全相同。

ReAct 删除后，归档记忆与知识库仍需明确所属服务。`backend/memory/memgpt_memory.py:29` 还单独写死归档集合的 1024 维，若保留归档检索，也必须一起迁移。现有 langgraph_agent 将自己的 rag 实例传入 MemGPTMemory，因此这一路会复用 API 进程内的模型，不能误算为额外第三份常驻模型。对外接口的兼容范围要逐项检查，不能根据当前前端没有调用就删除公开接口。

## 实施顺序

1. **建立部署验收工具。** 固定语料、教学数据库与研究问题，记录模型 revision、文档数量、镜像 digest、服务组和机器规格。先让坏配置、缺库和模型不匹配可以被准确检测。记录现有主链与事件/报告行为基线。
2. **迁移所有旧模块调用方，再删除 ReAct。** 将 API 的知识库调用迁往 MCP，提取文档工具与共享 LLM 客户端，明确内存读取接口。同步迁移前端路由类型、事件投影及测试。研究错误保持明确失败，证据拒绝仍禁止发布未通过内容。
3. **切换单份 CPU 轻量模型。** 加入模型、设备、线程、batch 和集合身份配置。执行非破坏性新集合迁移；核对检索质量、缺模型报错与重启恢复。
4. **完成生产打包和流量边界。** 修复部署入口、依赖、环境注入、模型缓存、数据库、健康检查及前端代理。增加活动任务准入、输入/上传限制和数据保留策略。
5. **在资源约束下运行完整验收。** 只有实际通过后，才把 PR 从 Draft 改为 Ready，并标注容量结果。

先保留 Milvus 作为待测方案，不凭静态审查宣称其低内存配置已经可用。如果预留系统空间后仍无法满足预算，再对比更轻的向量存储或外置方案。避免在没有测量前同时替换模型、数据库和全部执行层。

## 8GB / 4 CPU 完成判据

以下是完整容量目标。已经执行与尚未执行的项目分别记录在验收记录中。严格整机边界仍未验收。

- 在明确限定的 Linux 4-vCPU、全机内存不超过 8,000,000,000 字节的虚拟机，或等价可验证的全栈及系统资源边界运行，禁用 GPU。记录实际 cgroup/VM 限额、整组服务峰值和 OOM/重启计数。不能使用每容器各 8GB，也不能将 GPU 测试当 CPU 结果。
- 给系统保留至少 1GiB 的初始预算。记录主机 MemAvailable 与服务组实际峰值；如果达不到余量，判失败并调整方案，不能依赖持续 swap 才完成研究。该预算是验收目标，不是当前内存用量预测。
- 从空模型缓存和空应用数据目录验证可重复预置。然后禁网加载模型，核验教学库必要表、正确集合身份与全部服务 ready。数据目录已有内容时不覆盖，不重新生成用户数据。
- 完整运行一次冷启动后的固定研究，再连续运行至少五次研究。每次必须完成真实 SQL、RAG、搜索、Writer、证据关卡、Critic、组装与报告，核对原始数值、统计口径及引用。记录工具缓存命中，不能把历史回放当真实执行。
- 一个任务执行时再提交任务，验证准入上限及忙碌响应；覆盖同 session 重叠、工具异常与超时后的槽位释放，不能因异常永久占位或把两个 run 状态混在一起。
- 运行期间健康、事件推送与人工审批可用。验证 300 秒等待/轮次上限的原有契约，证据失败不能被新的错误处理绕过。自动检查与实际触发分支分开报告。
- 真实浏览器从输入到报告验证一次，检查 SSE 到达、重连补齐、状态流转、图表数值、引用悬停与跳转。通过部署入口访问，不绕过代理直连 API。
- 重启 API/MCP 后继续读取合法历史事件和报告；模型缓存与知识库、SQLite 持久化仍完整。每个 run 的终态与报告只属于同一次执行。
