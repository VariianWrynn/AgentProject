# 技术选型弹药 ×2

## 一、为什么不用 AutoGen / MetaGPT，而是 LangGraph 自建状态机？

**结论一句**：我需要的是可测、可降级、可审计的确定性编排，不是自由对话式协作。

**三个论据**：
1. **状态可控可测**：LangGraph 的 AgentState 是显式 TypedDict（30+ 字段），每个节点是纯函数 `run(state, llm) -> partial_state`——我能对 LeadWriter 的守卫回路写离线单测（脚本化假 LLM，毫秒级跑完 21 个用例）。AutoGen 的 agent 间自由对话没有稳定的中间表示，事实约束这种"检索后冻结证据集→写作强制引用"的硬约束没处挂。
2. **降级路径显式**：三层降级需要在图的边上做条件路由（quality<0.7→HITL、迭代≥3→强制收敛、检索空→RAG-only）。LangGraph 的 conditional_edges 就是干这个的；MetaGPT 的 SOP 流水线改控制流要动框架内部。
3. **面试/维护成本**：6 个节点每一个我都能画出输入输出和失败分支；框架黑盒出了问题（比如 AutoGen 的对话不收敛）只能调 prompt 碰运气。

**一个让步**：如果场景是"多 agent 探索式协作解决开放问题"（如代码仓库级重构），AutoGen 的自由对话模式确实更合适；我的场景是结构固定的报告生产线，确定性编排收益更大。

## 二、为什么不直接长上下文（把语料全塞进 prompt）？

**结论一句**：128K/1M 上下文解决的是"塞得下"，解决不了"可审计、可更新、成本"三件事。

**三个论据**：
1. **可审计性**：塞全文让模型"自由引用"，你无法验证它引的是不是原文——我的方案里每个数字回指到 chunk_id 精确匹配，40 题评测把无据作答率从 70% 压到 10%。长上下文模式下这个校验没有锚点（无 chunk 边界、无证据集冻结）。
2. **成本与延迟**：我的语料 9.1 万字 ≈ 13 万+ token，每问全量塞入按 deepseek-v4-pro 牌价单次输入就 ~$0.06，且随语料线性增长；检索方案每问只取 top-5 chunks（~2K token），语料涨 10 倍检索成本几乎不变。（完整成本对比见 perf 报告）
3. **更新频率**：财报季每季度新增几十篇文档，向量库增量 ingest 分钟级生效；长上下文方案每次变更都要重新组装/缓存全量 prompt，缓存失效成本高。
   另外有 lost-in-the-middle：忽略中段内容的问题在 100K+ 上下文里依然实测存在，检索 top-5 反而把信噪比做高了（hit@5 96.7%）。

**一个让步**：如果语料只有几千字且极少更新（比如单份合同问答），直接塞上下文更简单，没必要上向量库——RAG 的价值随语料规模和更新频率增长。
