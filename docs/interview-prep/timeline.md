# 时间线叙事稿 — v0 → v3 里程碑

> 目的：消掉"14 个月无演进"的疑点。叙事线：v0 ReAct → 评测暴露问题 → 拆角色 → 事实约束 → 降级 → 记忆。
> ⚠ 标注说明：`[git]` = 仓库可查证的提交/PR 日期；无标注段为入库前的原型期，表述已按"本地原型/学习期"口径处理，面试时如实说明即可。

## 里程碑表

| 版本 | 时间段 | 内容 | 触发动机（上一步暴露的问题） |
|------|--------|------|------|
| **v0 原型期** | 2025.06 – 2026.03 | 课程学习 + 本地原型：单体 ReAct 循环（Plan→Act→Reflect）、DuckDuckGo 搜索、初版 RAG demo；未系统化入库 | 起点：验证"检索+推理循环"能不能出报告 |
| **v1 工程化** | 2026.03.31 – 04.12 `[git]` | wk1: 工业级 RAG 管线（bge-m3 + Milvus IVF_FLAT、512 token 分块、SHA-256 去重）→ wk1: ReAct 引擎 + Redis 会话记忆 → wk3: Text2SQL + LangGraph 5 节点状态机 → wk4: 30 题全链路评测套件 + Docker 化 | v0 的脚本没法回归测试；ReAct 单循环对结构化查询（SQL 类）路由混乱 |
| **v1.5 领域化** | 2026.04.12 – 04.14 `[git]` | 能源行业落地：Bocha 中文搜索替换 DuckDuckGo、能源库 energy.db（1,389 行）、Router 5 类能源意图；多 key 并行提速 | 通用 demo 无法回答真实行业问题；单 key 限流拖慢多角色并发 |
| **v2 多智能体** | 2026.04.14 – 04.27 `[git]` | 拆 6 角色（ChiefArchitect/DeepScout/DataAnalyst/LeadWriter/CriticMaster/Synthesizer）+ asyncio 并行搜索；OPT-001~005 五项优化：Critic 一致性守卫、PDF 表格、**HITL 人工门控**、Router 误分类修复、**Layer3 降级兜底**（99/99 LLM 集成测试通过）；MemGPT 双层记忆（跨会话 top-1 0.6807） | 单 writer 长报告质量不稳定；30 题评测暴露 Critic 打分与 issue 数不一致、低质量报告直接出门 |
| **v3 事实约束** | 2026.08 `[git]` | 数据底座（37 篇真实语料/138 chunks）+ 冻结评测集（40 事实 + 50 意图）+ 事前约束改造（证据冻结 + chunk_id 绑定 + 引用回指校验）；错误率 27.5%→15.0%，无据作答 70%→10% | v2 的 CriticMaster 是事后审查——基线评测实测 70% 的语料外问题被编造作答，事后审查根本发现不了"数字对不对" |

## 口播版（60 秒）

"这个项目 14 个月里走了四个版本。最早是单体 ReAct 原型，验证检索加推理循环可行。2026 年 3 月开始工程化：Milvus RAG 管线、LangGraph 状态机、30 题评测套件——评测让我第一次看到路由混乱和质量不稳定。4 月拆成 6 角色多智能体并做了能源行业落地，加了 HITL 门控和三层降级，那一轮 99 个集成测试全过。但 8 月我做了一次更严格的评测——40 题、逐条证据锚定——发现了真正的硬伤：语料没覆盖的问题 70% 会被编造作答。这催生了 v3 的事前约束改造：证据集冻结、chunk_id 绑定、数字逐句回指校验，错误率从 27.5% 降到 15%，无据作答从 70% 压到 10%。每一版都是上一版的评测暴露的问题驱动的。"

## 关键防御点

- **为什么 5-8 月间隔？** 4 月底 v2 完成后进入使用期（自己作为分析用户跑真实问题），8 月的 v3 改造正是使用期发现"数字不可信"后立项的——版本间隔 = 使用反馈周期，不是停滞。
- **git 起点是 2026-03？** 2025.06 起为课程学习与本地原型（未入库），2026.03 工程化时才建仓——如实说，重点放在入库后 5 个月 20+ 个 PR 的密度上。
